# Git & GitHub Workflow Rules

## 1. Branch Safety
- Never commit directly to `master`. All work happens on a feature/topic branch.
- If asked to make changes while on `master`, create and switch to a new branch first
  (ask for a name or propose one, e.g. `feature/`, `fix/`, `chore/` prefix) before committing.
- Never force-push (`--force` / `--force-with-lease`) without explicit approval.
- Never rewrite history (`rebase -i`, `commit --amend`, `reset --hard`) on a branch
  already pushed to remote, without approval.
- Never delete a remote branch without approval.

## 2. PR Scope & Size
- Each PR must be **specialized**: a single logical change or feature — no bundling
  unrelated fixes, refactors, or features into one PR.
- Each PR must be **no more than 250 lines of changes** (additions + deletions combined).
- If a change naturally exceeds 250 lines or spans multiple concerns, split it into
  multiple smaller, sequential PRs and propose that breakdown before starting.

## 3. Commits
- Keep commits atomic and scoped — one logical change per commit.
- Use a consistent commit message convention (e.g. Conventional Commits: `feat:`, `fix:`, `docs:`).
- Never blindly `git add .` — review the diff/file list before staging.
- Never commit secrets, credentials, `.env` files, or API keys. Check before staging.

## 4. Pushing to Remote
Before any action that touches the remote (push, PR, editing a PR/commit already on remote):
- Provide a short summary of what changed and why.
- Explain the action about to be taken.
- Wait for explicit approval before executing.

## 5. Opening a Pull Request — two-step approval
**Step 1 — Propose the PR** (before touching remote):
- Proposed PR **title**
- Proposed PR **description**
- **List of changed files**

**Step 2 — Open the PR:**
Only after Step 1 is explicitly approved, open the PR remotely.
- Default PR mode: **draft**, unless the user asks for ready-for-review.

## 6. Merging a Pull Request — double confirmation
- Never merge a PR automatically.
- Approval to *open* the PR does **not** count as approval to *merge* it —
  merging requires its own, separate, explicit confirmation.
- Confirm CI checks are passing before the merge is even proposed.
- Default merge strategy: **squash merge**, unless the user asks for a merge commit
  or rebase-merge.

## 7. Other PR/Issue Actions
- Never close/reopen PRs or issues without approval.
- Never edit or dismiss another person's review comments without approval.

## 8. Destructive Actions
- Before any destructive action (`reset --hard`, deleting files, discarding local
  changes, `git clean -fd`), summarize what will be lost and ask first.
- On push/PR conflicts, stop and report — never auto-resolve without approval.

## 9. Claude-Generated Documentation
- Any `.md` documentation files **generated by Claude** (notes, summaries, design
  docs, etc.) go in a local `docs/` directory.
- Add `docs/` to `.gitignore` so Claude-generated docs are never committed or pushed.
- Pre-existing project markdown (`README.md`, existing `docs/` content authored by
  the team, etc.) is untouched by this rule and stays wherever it already lives.

## 10. Restricted Scope (never without approval)
- No changes to CI/CD config or GitHub Actions workflows.
- No changes to repo settings.
- No tagging releases or bumping versions.
